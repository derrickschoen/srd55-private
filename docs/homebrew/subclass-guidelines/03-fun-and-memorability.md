Purpose: turn a balanced schedule into a subclass players can recognize, choose, remember, and enjoy across an entire session.

# Fun and memorability

## Begin with an unserved fantasy

Write the fiction before the arithmetic. Describe who the character is, what they visibly do, and how the scene changes when they do it. A theme is not enough: a color, damage type, creature association, profession, or mood becomes a subclass only when it produces a repeated play pattern.

Prefer a fantasy that the host class and its SRD subclass do not already serve. The safest originality is a new relationship between familiar rules pieces, not a new vocabulary for an existing play loop. Ask which player desire currently has no home and why this host class is the natural chassis for it.

For every mechanic, finish the sentence *In the fiction, this happens because…* If the answer is only that an unexplained force does it, either strengthen the fiction or remove the mechanic. The reverse test matters too: if the rule creates self-injury, failure, coercion, or another strong tone, the one-sentence pitch must disclose that experience.

## Establish the identity loop at level 3

The subclass must become itself in the session it is chosen. Its first feature should be an operable engine, not a promise of a later feature. State the loop in four beats:

1. **Observe:** what scene fact or resource state does the player notice?
2. **Choose:** what meaningful decision do they make?
3. **Act:** which normal class action carries the feature?
4. **Change:** what becomes visibly different after resolution?

The loop should recur often enough to become recognizable without firing on every die. Later features should deepen it: a new target, a different spend, improved reliability, faster activation, wider scene use, or a higher-tier consequence. Unrelated widgets dilute memory and consume tracking budget.

Level 3 commonly holds a second compact feature in the SRD, but do not mistake multiple headings for multiple engines. One loop plus spell access, a proficiency, a ribbon, or a small support rule is teachable. Three interlocking subsystems are not.

## Create decisions, not merely larger totals

Players remember choosing between live alternatives more readily than they remember a permanent modifier. Put the subclass's fun in one recurring question: spend or hold, move or protect, concentrate force or spread it, accept risk or bank safety. A choice made once and then forgotten is customization, not moment-to-moment agency; it should not be advertised as the subclass's active loop.

Do not add decisions everywhere. Every option visible during a turn consumes time even when unused. Use one decision-bearing signature feature, then make support features passive, automatic, or attached to a single obvious trigger. At high tiers, increase consequence more often than option count.

## Keep resources alive

A resource is alive when the player repeatedly feels a real tension about it. Several shapes can work:

- **Variable spend:** one pool accepts small or large payments, trading efficiency for urgency. This yields several tactical expressions from one rule.
- **Accumulate toward risk:** one meter rises through participation, unlocks stronger effects, and threatens a bounded consequence. The meter must be the subclass's only tracked quantity; cap both gain and punishment, and never let one bad roll impose several losses.
- **Retrainable menu:** choose a small set of simple options at acquisition and permit replacement on level-up. Build depth lives between sessions; each chosen option resolves quickly at the table.
- **Native-resource conversion:** let an existing class pool buy a new effect. This is usually more legible and dip-resistant than adding a second pool.
- **Long-rest pool with a top-up:** give enough uses to create spend/hold decisions during ordinary play, with a modest Short Rest recovery if desired. Do not make the subclass depend on a table taking several Short Rests.

Variable spend, risk accumulation, and a menu are alternatives, not ingredients to combine. One subsystem is normally enough. If the feature requires a pool, thresholds, marks on targets, and a combat option list, the design has confused depth with state.

Avoid a lone once-per-Long-Rest showpiece as the defining loop. It encourages hoarding on long days and immediate discharge on one-fight days. If the fantasy requires a rare transformation, give the subclass a smaller repeatable expression of the same fantasy.

## Respect the parent class

The subclass inherits its complexity budget from its parent. A player choosing a direct, low-bookkeeping class did not consent to a stance chart, several counters, and a menu each round. A player choosing a class with an existing resource or option engine can accept an interaction with that engine, but still should not manage a parallel character sheet.

Before adding a feature:

- inventory the parent's Actions, Bonus Actions, Reactions, concentration, attack riders, and between-turn state;
- use the abilities the parent already advances; never introduce a new required score;
- avoid locking the subclass to one equipment category unless the fantasy cannot exist otherwise, and provide a clean path when treasure changes;
- scale a companion from the character's investment and class level rather than freezing it at acquisition;
- attach later improvements to the level-3 loop or parent engine.

A subclass should change how the class plays more than how well it performs. It may redirect a native action or resource; it should not erase the class's tradeoffs.

## Give the identity a whole-session presence

Combat, exploration, and social interaction form a coverage grid. A subclass may lean heavily toward one pillar, but should not leave the player with no subclass-facing choice in the other two. Walk through a negotiation, a journey, and two fights. Record when each feature could matter.

Ribbons are inexpensive ways to make the fantasy visible outside combat: an unusual sense, a narrow communication permission, a flavorful immunity, or an information tool. They are not inferior features, but they are not load-bearing combat value either. Keep two rules:

1. a whole subclass level cannot be only a ribbon; and
2. several ribbons together can become real power, so count their combined frequency and breadth.

Patch the base class's blind spots. A martial chassis benefits greatly from player-initiated information, movement, or social leverage. A full caster often already has those capabilities through spells; a useful subclass feature may instead save a slot, improve access, or make a thematic utility reliable.

Prefer non-combat rules the player can invoke. A minute-long examination, declared question, or purposeful travel procedure advertises itself. A permission that works only when a particular landscape, creature, or scenario appears asks the campaign to remember the subclass.

## Grow with the tiers

Tier 2 is where the loop should become dependable and expressive; many campaigns spend most of their time there. Put a highly enjoyable improvement in a commonly reached middle slot rather than withholding the best idea for the final feature.

Tier 3 changes the kinds of problems characters solve. Add a new verb, broader control, or better action economy instead of another small modifier. Design around long-range movement, strong information access, flight, and encounter-ending magic already being ordinary party tools.

A late feature whose whole value is one saving throw with no result on success is fragile against high-tier defenses. Prefer an effect that still changes position, terrain, tempo, or magnitude on a successful save. No-save scene control is correspondingly expensive; keep it bounded in area, duration, targets, or action denial.

Tier 4 turns are powerful and crowded. Prefer a decisive, simple culmination: remove friction from the established engine, make one result reliable, extend an effect to a scene, or unlock a costly second use. A final-slot subsystem is both late to learn and unlikely to receive enough playtesting.

## Exercise first-party restraint

A design reads as first-party when it uses familiar rules language, names every action and limit, and lets one clear idea carry the option. Novelty is not proportional to new terms. Restraint, layout discipline, and short adjudication paths build trust.

Presentation is part of rules delivery. Put features in schedule order, use consistent headings, separate flavor from operative text, and expose option summaries without forcing an in-turn page search. A familiar fantasy that existing mechanics underdeliver may be treated as unserved, but repair it from the fantasy statement rather than copying an earlier mechanical shape.

Calibrate a new design slightly under the comparable official power line until play establishes otherwise. Within these clean-room files, the legal comparator is the same-class SRD subclass at the same slot. Being a little weak is correctable without disrupting a table; a high-side outlier multiplies through feats, equipment, party support, and multiclassing before its defect is visible.

Calibrating under the comparison line does not mean making the design dull. Protect the dial that makes the fantasy work. Every feature has frequency, action cost, range, duration, targets, reliability, and magnitude. Name the identity-bearing dial before balancing. Reduce a different dial first. If movement across the battlefield is the promise, do not balance by shrinking movement to irrelevance; lower damage, uses, duration, or targets instead. If the protected dial itself violates a structural guarantee, redesign the loop rather than pretending the fantasy excuses it.

## Playtest for usage

Balance and enjoyment are independent. A numerically correct feature that nobody activates has failed. Record behavior, not only damage:

- How many rounds was the feature relevant, offered, chosen, and resolved?
- When offered but declined, was that a meaningful choice, hoarding, action congestion, or forgotten text?
- Did the player say the turn in one pass, or reopen the rule?
- Did another player become quieter because the subclass occupied their role?
- Did the subclass appear outside combat without the facilitator arranging a special scene?
- After the fifth use, did the loop remain satisfying and fast?

Test at acquisition, in the most-played middle tier, at level 11, and at level 17. Mark any unplayed tier as provisional. Change a feature because observed use falsified an expectation, not because its average looked unfamiliar.

## Anti-pattern index

This index includes experience failures that overlap `04-failure-taxonomy.md`; overlapping entries point there instead of repeating the full diagnosis.

| Anti-pattern | Fast response |
|---|---|
| Overloaded level 3 | Keep one engine and at most compact support; move later expressions to later slots. |
| Dead level | Give every slot a substantial feature or an honest upgrade; a ribbon alone does not fill a slot. See F15. |
| Capstone too late | Put the repeatable fantasy at 3 and a memorable improvement in the middle; reserve only culmination for the final slot. |
| Feature tax | Remove a compulsory rule that exists only to occupy a slot or enable a later feature the player cannot yet enjoy. |
| Once-per-day showpiece | Provide a repeatable smaller loop and stress both hoarding and one-fight-day burst. See F10. |
| Pseudo-choice | Let the choice recur in play or make the selection replaceable at level-up; label permanent specialization honestly. |
| Target-type dependency | Add a general baseline and treat the narrow target as an enhancement. See F11. |
| Equipment lock-in | Key the fantasy to a broader action or provide a deliberate retuning path when equipment changes. |
| Stat drift or multi-ability dependence | Use an existing primary ability, class DC, or class-level value. See `01-power-budget.md` heuristic 12. |
| Action-economy collision | Draft the whole turn and move or fold the action cost. See F6. |
| Static companion | Scale defenses, offense, DCs, and utility from class investment; avoid an acquisition-level stat block forever. |
| Damage-rider-only | Add a new verb and player-initiated non-combat presence. See F15. |
| Theme incoherence | Require a visible fictional cause for each rule and a rule expression for each promise. See F14. |
| Initiative-start exploitation | Audit pre-fight setup, stalling, repeated initiative, and whether the trigger should instead be a per-rest activation. See F4 and F10. |
| Complexity mismatch | Reduce state and move choices out of the turn. See F13. |
| Catalogue padding or incomplete rules | Remove repeated filler; supply every action type, trigger, target, duration, limit, and scaling clause before playtest. |
| Kit sprawl | Keep one subsystem and make later features improve it. See F13 and F15. |
