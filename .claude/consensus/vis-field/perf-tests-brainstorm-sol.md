# Performance-test brainstorm

No files were changed. All proposals preserve test membership and assertions.

## Measurements

- Main’s recorded replay+detection pair: **33.59 s**, including **30.31 s test execution**.
- `detection-reactions.test.ts`: **2.97 s total**, but only **48 ms testing**; import was **1.29 s**.
- `arena-basis-brutal-b.test.ts`: **21.38 s total**, **17.72 s testing**. Its 33 frozen-room executions cost roughly 0.2–1.2 s each.
- `room-generator-los-cover.test.ts`: exceeded 30 s before completion. Four repeated nine-room checks alone cost **3.589 + 4.093 + 4.298 + 3.721 = 15.70 s**.
- `d583-contract-inventory.test.ts`: every inventory construction costs **3.63–4.03 s**, because it recursively reads and parses every TypeScript file.
- `d569-blind-experiment.test.ts`: exceeded 30 s during its first 17 tests; repeated manifest checks cost **1.53–3.11 s each**.
- `d569-v5.test.ts` could not execute in this read-only sandbox because its top-level setup calls `mkdtemp`; inspection still exposed two serial top-level `runArena` calls.
- The supplied **343 s** `ai-dm-conversation` measurement was not rerun under the six-minute budget.

## Ranked proposals

| Rank | Type | What is slow and why | Concrete change | Expected saving | Strength/risk | Files |
|---:|---|---|---|---|---|---|
| 1 | Test/tool cache | D583 rebuilds the complete filesystem dependency graph around eight times, at ~3.7 s each. | Extract `buildDependencyIndex()`. Build and freeze it once in `beforeAll`, then inject it into every changed-path/Git-seam case. Keep one test exercising default filesystem discovery. | **25–28 s**, roughly 75–85% of this file. | No assertion removed; every closure/deletion/Git behavior remains independently tested. The one uncached test prevents a self-validating fixture. | `tools/d583-contract-inventory.ts`, `tests/unit/tools/d583-contract-inventory.test.ts` |
| 2 | Pure test | Replay constructs the same four-round gate **13 times**. Individual mutation tests cost ~1.6–2.4 s; PLAYABLE-EXIT costs **3.716 s**. | Build the default gate once, deep-freeze it, and give each test a fresh `structuredClone`. Keep separate cached gates for the two non-default parameter combinations. Every test still calls `replayBundle` on its own candidate. | Conservatively **15–20 s** from the 33.6 s pair. | Mutation isolation is mandatory; never share a mutable bundle. This preserves every corruption oracle and full replay. | `tests/unit/vtt/replay.test.ts` |
| 3 | Test/tool cache | D569 manifest mutations repeatedly regenerate/hash 40 rooms and reread frozen inputs: **1.5–3.1 s per validation**. | Introduce an immutable “verified input proof” prepared once from the declared access object. Structural candidate validation reuses it; tests that mutate KB/fixture bytes construct a fresh proof. Split manifest, state-machine, analysis, and sealing sections into files. | Likely **25–40 s** and better worker utilization. | All 32 pins and every regeneration run once; hostile-access tests remain uncached. Keep the 100,000-resample reproducibility test fully independent. | `tools/d569-blind-experiment.ts`, `tests/unit/tools/d569-blind-experiment.test.ts`, new focused test files/helper |
| 4 | Pure test | LOS/cover regenerates the same nine versioned rooms in five groups; four groups alone cost **15.70 s**. The 96 determinism cases are also serialized inside one file. | Prebuild/deep-freeze the nine rooms per difficulty, run all existing membership/path/productivity assertions against them, and retain the explicit two-generation determinism assertion. Split the 96 property rows into standard/hard/brutal files. | Estimated **15–35 s**, depending on cache reuse; measure before accepting. | Same seeds and assertions. Freezing prevents hidden mutation. Do not replace the two independent determinism generations. | `tests/unit/vtt/room-generator-los-cover.test.ts`, new shared helper and three property files |
| 5 | Pure test | Arena’s 33 executions are serialized in one file; hard/brutal/brutal-b groups cost about **7.2/4.6/4.1 s**. | Split execution membership by family, sharing helpers and frozen parsed initial states. Keep byte pins and structural membership together. | With three workers, approximately **10–12 s** wall saving versus 21.38 s. | Assertions and seeds remain identical. Watch memory: each worker imported ~1–2 s of engine code. | `tests/unit/vtt/arena-basis-brutal-b.test.ts`, new arena helper and family files |
| 6 | Engine cache — **owner decision** | Reducer steps always create a new outer state, invalidating state-identity WeakMap caches. Cover partly compensates with a bounded signature cache; visibility-field is reportedly state-identity-only. This compounds across replay and the 343 s conversation. | Key terrain caches from structurally shared geometry references; key creature/visibility caches from explicit visibility-affecting epochs or composite identities. Invalidate only on token movement, life/size/sense/effect/light/blocker/world-object changes. | The visibility-field regression suggests **8–12%** recoverable on replay; potentially **30–70 s** on the 343 s test, but profile first. | Highest correctness risk. Require cache-hit counters plus mutants for every invalidator and cached-vs-uncached equivalence. | `src/combat/cover.ts`, in-flight `src/combat/visibility-field.ts`, possibly `src/combat/encounter.ts`, cache tests |
| 7 | Pure test | D569-v5 performs two awaited `runArena` productions at module import, forcing unrelated validator tests to pay both before collection. | Move cancellation and timeout productions into separate focused files/hooks so Vitest can schedule them concurrently; move consumer evaluation into the timeout describe. | Up to half the two integration-fixture setup wall; benchmark required. | Preserve the actual `runArena` path and all downstream consumer assertions—do not replace rows with generated expectations. | `tests/unit/tools/d569-v5.test.ts`, new helper/integration files |
| 8 | Test/tool cache | The 3×3 AI-DM smoke performs nine sequential engine rounds. It repeatedly hashes the same starting room and rebuilds geometry-dependent projections. | Cache immutable room digests/decoded fixtures locally, then apply proposal 6 to engine queries. Keep the exact 3-room/3-round test intact. | Local caching is probably only seconds; engine caching is the meaningful **10–20%** candidate. | Splitting it into one-room tests would lose room-transition/session-continuity coverage. That requires owner approval and is not recommended. | `tools/ai-dm-conversation.ts`, `tests/unit/tools/ai-dm-conversation.test.ts`, engine cache files |
| 9 | Config — **owner decision** | Current default is forks, `isolate:false`, `maxWorkers:8`. Loaded runs create many near-5 s failures. Vitest already starts historically slow files first, but built-in sharding hashes by filename/count, not duration. | A/B heavy suites at 3–4 workers versus 8; keep ordinary suites at 8. For distributed runs, use longest-processing-time shard manifests from persisted durations. Separately trial `experimental.fsModuleCache`; do not combine experiments. | Worker cap may reduce flakes more than wall time; duration-balanced shards can reduce tail substantially. Module caching targets the observed 1–7 s import costs. | Gate topology and experimental caching need owner approval. Preserve `isolate:false` audits because shared-module order bugs already exist. | `vitest.config.ts`, `package.json`, optional sequencer/gate script |

## Explicit low-value or rejected ideas

- Do nothing to detection-reactions: **48 ms** of test work means fixture reuse saves essentially nothing and adds contamination risk.
- Do not split detection; duplicated 1.29 s imports would make it slower.
- Do not raise more timeouts, reduce seeds/rounds, remove renderer options, skip tests, or replace expectations with current output.
- Do not blindly switch pool type or `configLoader runner`; loader choice affects configuration startup, not the dominant engine work. A forks/threads A/B was unavailable because forks could not create their temporary SSR directory in this read-only sandbox.
- `it.concurrent` does not parallelize synchronous CPU work within one worker; file-level splitting is the useful boundary.
- Vitest already orders historically long files first. Custom ordering has little value unless real multi-process sharding is introduced.
